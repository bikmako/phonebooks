# Проверка обновления на iPhone без рабочих данных

Проверка проводится на отдельном HTTPS-хосте, а не на рабочем PhoneBooks и не на `phonebooks-demo`. Подготовленные архивы ничего не публикуют сами.

В GitHub откройте PR #7 → Checks → Test PhoneBooks → соответствующий Actions run. После успешного шага тестов обновления появится артефакт **iphone-update-device-test**. Скачайте и распакуйте внешний архив артефакта: внутри три ZIP для этапов 01/02/03, эта инструкция и SHA-256. В Direct Upload передавайте один нужный вложенный ZIP, а не весь внешний архив с тремя этапами. Если сборка ещё идёт, дождитесь шага Upload iPhone device test packages.

Локальное воспроизведение в среде с Node, Python 3 и tar: `npm ci`, `npm run test:updates`, затем `node tools/prepare-device-test.js`. Результат — `work/device-test-artifacts/`; сетевой публикации команда не выполняет.

## Изоляция

1. В рабочем приложении можно только скачать внешнюю полную резервную копию в «Файлы». Не переносите её на тестовый сайт. Не очищайте Safari, не удаляйте рабочую PWA и не нажимайте сброс данных.
2. Создайте **новый** Cloudflare Pages Direct Upload project, например с именем `phonebooks-update-check-<ваш-суффикс>`. Не используйте существующий `phonebooks-demo`, GitHub Pages или настройки его Branch control. Для тестового проекта не требуется подключение Git.
3. Проверьте адрес: отдельное имя хоста вида `<новый-проект>.pages.dev`, HTTPS и другой `location.origin`. Другой путь или другой репозиторий под `bikmako.github.io` недостаточны: origin у них общий.
4. Все три архива загружайте по очереди только в этот новый проект. Адрес и путь приложения `/phonebooks/` между загрузками должны оставаться прежними. В архиве есть корневая страница с меткой этапа и папка `phonebooks/`; откройте `/phonebooks/` после публикации и убедитесь, что это выбранный тестовый хост.

IndexedDB и localStorage разделены по origin. На таком стенде база с именем `phonebooks` относится только к тестовому хосту и не является базой рабочего сайта. Нельзя считать заменой этой изоляции второй ярлык PWA, приватную вкладку, hash или query-параметр.

## Этап 1 — предыдущая опубликованная версия

Загрузите `01-previous-published.zip`. Он содержит предыдущую React/Vite-сборку `832972e`; её worker совпадает с опубликованным `phonebooks-v9-0efdf641` по SHA-256.

- В обычном Safari откройте тестовый `/phonebooks/`. В настройках задайте название бизнеса «ТЕСТ ОБНОВЛЕНИЙ». Добавьте только вымышленные остатки, телефон, продажу, аксессуар и ремонт; рабочую резервную копию не импортируйте.
- Создайте тестовую точку восстановления и скачайте полную копию именно тестовых данных в «Файлы». Запишите количества и суммы либо сделайте скриншоты для сравнения.
- Откройте новую покупку, введите узнаваемый черновик, подождите несколько секунд для обычного автосохранения. У старой версии нет нового механизма принудительного сохранения перед обновлением.
- Через «Поделиться» → «На экран Домой» добавьте сайт с именем **PhoneBooks ТЕСТ**. Проверьте, что открыт именно тестовый hostname. Не удаляйте и не изменяйте рабочий ярлык.
- Дайте приложению загрузить ресурсы, откройте его без сети и проверьте, что тестовая база доступна. Верните сеть перед первым переходом со старого worker.

## Этап 2 — первый переход на безопасные обновления

Загрузите `02-safe-current.zip` в тот же тестовый проект, без смены hostname и `/phonebooks/`.

1. Не ожидайте нового уведомления в уже открытом старом интерфейсе: его код не содержит этой функции. Не должно быть и внезапной перезагрузки открытой формы.
2. Сохраните нужные поля/дождитесь автосохранения черновика. Закройте тестовые вкладки Safari и полностью завершите **тестовую** PWA через переключатель приложений; снова откройте её с сетью. Если iOS сохранила старый документ в памяти, один раз вручную перезагрузите именно тестовый URL в Safari. Рабочее приложение не трогайте.
3. Возможны два штатных варианта: появится «Доступно обновление» либо полностью подготовленный новый worker активируется после закрытия всех окон и приложение сразу откроется новым. Второй вариант не является пропущенной обязательной перезагрузкой.
4. Если уведомление есть, закройте остальные окна тестового `/phonebooks/` и нажмите «Обновить». Проверьте одну перезагрузку, прежние записи, суммы, точку восстановления, настройки и черновик покупки. Повторно откройте приложение и убедитесь в отсутствии циклов reload.
5. В авиарежиме повторите запуск. Верните сеть, скачайте новую тестовую полную копию и проверьте содержимое. При необходимости восстановите тестовую копию на этом же стенде через штатный предварительный просмотр; не используйте рабочий файл.

Новый протокол не может задним числом исправить поведение уже запущенного старого worker. Первый ручной переход проводите с устойчивой сетью и внешней тестовой копией. Проверки обрыва подготовки ниже относятся к новому протоколу; на исходном legacy-worker HTML по-прежнему загружается из сети.

## Этап 3 — обновление уже нового интерфейса

Загрузите `03-safe-repeat.zip`. Это тот же код приложения с отдельной тестовой меткой сборки в HTML и заново вычисленными контрольными суммами; метка не меняет учёт или хранилища. Она нужна, чтобы повторное размещение одинакового кода действительно создало новую версию worker.

- В открытой PWA вернитесь из фона с интернетом, дождитесь подготовленного обновления. При частом переключении повторная сетевая проверка может быть ограничена одной минутой; периодическая — каждые 15 минут видимой работы.
- Нажмите «Позже», переключитесь между приложениями и повторно откройте тестовую PWA: предложение не должно возвращаться постоянно. Эта версия откладывается на четыре часа в сессии вкладки; iOS может завершить сессию, выгрузив документ. Для следующей проверки дождитесь срока либо разместите другой тестовый этап 02/03: другая версия предлагается отдельно. Не очищайте хранилища ради повторного уведомления.
- Откройте покупку или продажу, измените поля и нажмите «Обновить». В подтверждении выберите отмену: поля и версия должны остаться. При согласии новый черновик покупки/продажи сохраняется; несохранённое редактирование существующих записей и прочие формы нужно сохранить заранее либо явно согласиться заполнить их заново.
- В форме ремонта проверьте отмену подтверждения, затем сохраните ремонт обычным действием до обновления. В открытом просмотре импорта обновление должно блокироваться до завершения/отмены импорта.
- Откройте тестовую PWA и тестовый `/phonebooks/` в Safari одновременно: приложение должно попросить закрыть другое окно, не перезагружая его само. После закрытия повторите обновление.
- Дайте обновлению полностью подготовиться, отключите сеть и примените его: подготовленная версия должна открыться офлайн с теми же данными. Отдельный повтор сценария можно провести, переключая этапы 02/03 на стенде; это тест, не инструкция отката рабочей версии.
- Проверьте портрет/альбом, safe-area, клавиатуру, большие шрифты, светлую/тёмную тему, возврат после сна. Уведомление должно занимать место в потоке, а кнопки форм оставаться доступными через прокрутку.

Для обрыва загрузки новой версии сначала разместите следующий тестовый этап, затем отключите сеть во время его подготовки. Старая рабочая оболочка должна остаться доступной; после возвращения сети повторите проверку. Если скачивание успело закончиться, это проверка применения уже подготовленной версии, а не прерванной загрузки.

## Что записать в результатах

Версия iOS, модель iPhone, hostname стенда, этапы до/после, режим Safari или «На экран Домой», число открытых тестовых окон, состояние сети, количества/суммы до и после, наличие черновиков и результат восстановления тестовой копии. Ошибку снимите на видео или скриншот; передайте данные из тестовой базы, не реальные клиентские записи.

После проверки можно удалить только тестовую PWA и новый тестовый проект. Не используйте глобальную очистку истории/данных Safari: она может затронуть рабочий сайт. Автоматизированный мобильный WebKit не заменяет эту проверку установленной PWA на физическом iPhone.
