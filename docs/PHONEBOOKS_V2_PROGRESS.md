### Как работает этап 2

- Team использует Supabase Auth через Worker. Cookie сессии имеют флаги `Secure` и `HttpOnly`. Список пространств, выбранное пространство и видимые приглашения приходят одним ответом с сервера. Создавать и отзывать приглашения может владелец пространства.
- Владелец пересылает ссылку на Team сотруднику. После входа с нужной подтверждённой почтой сотрудник видит приглашение в аккаунте. Письма подтверждения адреса и восстановления отправляет Supabase. Автоматическая рассылка командных приглашений не подключена.
- Solo и Team используют разные имена хостов. При переходе из Solo приложение ждёт подтверждения записи в IndexedDB. Ссылка на Team появляется в настройках только указанной сборки Solo. Данные Team на этом этапе не сохраняются в браузерное хранилище.
- Проверки на локальном HTTPS-стенде используют браузеры, тот же Worker, реальные миграции PostgreSQL в PGlite и тестовый ответчик Auth с почтовым ящиком. Smoke-тест Solo меняет локальные данные, переходит в Team, возвращается и перезагружается без сети.
- Успешны сборки Solo и Team и локальная упаковка Worker через Wrangler с `--dry-run`. Устранён сбой запуска стенда обновлений на Windows. После исправления прошли 12 проверок установки PWA, сохранения настроек и повторной записи после ошибки в четырёх браузерных профилях.

### Как запустить проверки

```sh
npm ci
npx playwright install chromium firefox webkit
npm test
npm run test:team
```

Для браузерного стенда нужен `openssl` в PATH. Стенд слушает только loopback, создаёт временный HTTPS-сертификат и синтетические аккаунты.

### Проверки перед закрытым пилотом

- Настроить отдельный Team-хост через `wrangler.phonebooks-team.toml`. Для сборки использовать `npm run build:team`. Worker ожидает `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` и `PHONEBOOKS_SOLO_URL`. При включённой CAPTCHA передать `TURNSTILE_SITE_KEY` и настроить секрет на стороне Supabase Auth.
- Проверить на выделенном Supabase staging миграции из `supabase/migrations/`. Включить обязательное подтверждение почты, задать Team-хост в Site URL, загрузить два шаблона из `supabase/templates/` и проверить доставку реальных писем через настроенный SMTP. [Документация Supabase по шаблонам](https://supabase.com/docs/guides/auth/auth-email-templates)
- Собирать изолированную тестовую копию Solo с `VITE_PHONEBOOKS_TEAM_URL`, указывающей на Team. Подтвердить возврат в нужную Solo PWA и сохранность данных на физическом устройстве.
- Добавить управление действующими участниками и защиту последнего владельца перед пилотом. Общий склад, операции и статистика зависят от серверной модели данных этапов 3–5.

## Оставшиеся этапы

На этапе 3 сверены остатки, касса, выручка, себестоимость и прибыль на синтетической старой базе. Часть контрольных документов проведена в локальной PostgreSQL, чтобы сверить суммы с Solo. Проверены отмена и повтор транзакции, параллельные записи каталога, восстановление старой и новой копии, изоляция предприятий, версия остатков и агрегирование по серверному автору.

### Точка продолжения

Перед закрытым пилотом проверить миграции и нагрузку на отдельном Supabase staging, настроить секрет переноса и подтвердить доставку реальных писем. Измерить и при необходимости добавить постраничную выдачу долгих дельт и перенос больших копий. Подключить сигналы Realtime после проверки инфраструктуры. Текущий офлайн-просмотр работает в открытой вкладке. Этап 5 добавит управление участниками, индивидуальные разрешения и представление статистики сотрудника. Пользовательские сценарии возврата и бронирования остаются отдельными задачами ТЗ.
