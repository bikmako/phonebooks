# Безопасные обновления PhoneBooks

Изменения предназначены для React/Vite-сборки из `app.html`. Готовая историческая сборка в корне, `backup/original-build/`, настройки Cloudflare и workflow публикации Pages не изменены. PR сам ничего не публикует: существующий Pages workflow запускается при push в main или вручную; этот PR не сливается автоматически.

Демоверсия проверена отдельно чтением ветки `feat/isolated-sales-demo` (на момент проверки `746d80a`): она использует `build:demo`, `dist-demo`, `sw-demo.js`, базу `phonebooks-demo` и ключи `phonebooks.demo.*` на другом origin. Эта ветка не изменяется и не сливается. В основной ветке нет генератора демоданных и команды `build:demo`. В GitHub уже подключена интеграция Cloudflare `phonebooks-demo`; её проверка на исходном коммите `832972e` завершилась ошибкой ещё до этой работы. Настройки веток автопубликации Cloudflare недоступны через имеющееся подключение, поэтому их нельзя считать проверенными. Этот PR не выполняет команд публикации Cloudflare и не меняет её конфигурацию.

## Как получает обновление пользователь

Постоянный адрес, origin и путь приложения остаются прежними. Переустановка PWA не нужна. Проверка `registration.update()` выполняется при запуске, каждые 15 минут видимой работы, при возврате фокуса/видимости/из bfcache и после восстановления сети. Частые возвращения ограничены одной сетевой проверкой в минуту; событие восстановления сети запускает отдельную попытку. В скрытом документе проверки не выполняются.

Service Worker получает идентификатор от содержимого файлов офлайн-оболочки и собственного кода. Изменение файла без изменения его имени тоже меняет версию. В сборку включены SHA-256 каждого файла оболочки, включая HTML, модули, шрифты, иконки и OCR/штрихкод-ресурсы. Сжатый OCR-словарь может отдаваться хостингом как файл или HTTP gzip: проверяются две точные контрольные суммы, исходная и распакованная. Это контроль согласованности сборки, а не криптографическая подпись издателя.

Новый worker проверяет и кеширует всю сборку до перехода в `installed/waiting`. Неудачная установка удаляет только собственный незавершённый кеш. Старая версия продолжает работать. Навигация и ресурсы активной версии читаются из одного её кеша: HTML из сети не подменяет его во время работы.

После подготовки появляется уведомление «Доступно обновление». Оно занимает место в потоке документа; при открытии общего Modal переносится в его прокручиваемую область. Оно не перекрывает нижнюю навигацию, кнопки формы и safe-area. «Позже» скрывает предложение этой версии на четыре часа в текущей сессии вкладки, в том числе после reload; новый подготовленный релиз предлагается отдельно. Через четыре часа предложение возвращается в видимом приложении или при следующем возвращении. При запрещённом sessionStorage отсрочка работает до закрытия документа. Без установленного обновления офлайн-уведомления нет; уже полностью готовое обновление можно применить офлайн.

## Что происходит после «Обновить»

1. Повторно проверяются waiting-worker и наличие всех файлов его кеша.
2. Открытая покупка, продажа, любой общий Modal или изменённое название бизнеса требуют подтверждения. Для осторожности подтверждение запрашивается даже для ещё пустой открытой формы. При отмене документ, поля и текущая версия остаются на месте.
3. Последнее состояние черновиков **новой** покупки и продажи записывается синхронно, без ожидания обычного debounce. Ошибка localStorage останавливает обновление. Несохранённые поля редактирования существующих записей и остальных форм не имеют автоматического черновика: подтверждение явно предупреждает, что их придётся заполнить заново. Выберите «Отмена» в подтверждении, сохраните форму и повторите обновление, чтобы их не потерять.
4. Блокируются новые изменения учётного состояния; ожидается очередь сохранений и завершение транзакции IndexedDB. Ошибка записи или открытый просмотр импорта блокируют активацию. Во время применения интерфейс временно получает `inert`, чтобы пользователь не успел изменить поля после сохранения черновиков.
5. Worker проверяет открытые окна того же scope. Остальные вкладки/PWA-окна нужно закрыть. Другие вкладки никогда не перезагружаются автоматически.
6. Только после этого отправляется `skipWaiting`. Одна перезагрузка выполняется только по смене контроллера на выбранный worker и только в документе, где нажали кнопку. Глобального обработчика «сменился controller — всегда reload» нет. Ошибка/таймаут снимают блокировку и не запускают фоновые перезагрузки.
7. Новый интерфейс, успешно открывший данные, подтверждает свою версию из HTML. Тогда worker может удалить старые кеши приложения. Он сохраняет кеши более новых installing/waiting-версий и не чистит ничего при наличии других окон. Кеши имеют scope в имени; legacy-кеш удаляется только после проверки всех его URL. Чужие кеши и другой scope сохраняются.

Если все окна закрыты, стандартный жизненный цикл браузера может активировать полностью установленный waiting-worker самостоятельно. Работающего пользователя в этот момент нет.

## Данные

Миграция не нужна. Схема IndexedDB остаётся `phonebooks`, версия 1, stores `state`, `backups`, `meta`, ключ состояния `current`. Система обновлений не открывает базу напрямую, не удаляет её и не импортирует данных. Существующий StoreProvider лишь завершает уже ожидающие сохранения.

Никакой массовой очистки localStorage нет. Существующие `phonebooks.data.v1`, `phonebooks.theme`, `phonebooks.draft.*` и сторонние ключи сохраняются. Только смонтированные новые формы записывают свой актуальный черновик после согласия пользователя. Резервные копии и recovery-снимки остаются в прежних stores и формате. Отсрочка уведомления хранится отдельно в sessionStorage под `pb-update:<scope>` и не попадает в бухгалтерские резервные копии.

## Первый переход со старой версии

До этого PR worker автоматически вызывал skipWaiting, удалял старые кеши на activate и обновлял HTML из сети. Уже открытый старый интерфейс не содержит кода нового уведомления. Изменить его поведение задним числом невозможно без принудительной навигации, поэтому её нет. При следующем обычном открытии/reload с сетью старый network-first worker отдаёт новый интерфейс, который уже управляет переходом. При закрытии всех окон полностью подготовленная версия может активироваться штатно. Переход с реальной сборки до PR проверяется отдельно.

Новые гарантии согласованности кеша начинают действовать после активации нового worker. Устранить прежнее поведение уже работающего legacy-worker самим PR невозможно.

## Ограничения и ручная приёмка

Автоматические профили iPhone WebKit и Android Chromium проверяют движки/размеры экрана, но не заменяют реальные установленные PWA на iOS/Android и Safari конкретной версии. iOS приостанавливает фоновые вкладки и может выгрузить worker; проверка возобновляется при возвращении. Браузер/ОС могут удалить локальные данные при нехватке места, очистке сайта или удалении приложения: система обновлений не даёт гарантии от этих действий. Полная новая сборка временно требует места рядом со старой, включая ресурсы сканера. Недостаток места прерывает подготовку.

Проверка остальных вкладок и последующее удаление кешей используют снимок `clients.matchAll`. Абсолютно атомарно запретить открытие нового окна в промежутке браузерный API не позволяет. Перед применением следует закрыть остальные окна приложения. При таймауте активации worker может завершить её позднее; автоматического reload после ошибки нет. Сохраните работу и повторно откройте приложение вручную.

До публикации клиентам на отдельном тестовом origin с тем же `/phonebooks/`:

- Сохранить внешнюю полную копию данных и проверить её импорт на отдельном тестовом профиле.
- Проверить первую установку и переход с текущей опубликованной версии на физических Windows/Chrome/Edge, Android PWA и iPhone/iPad Safari + «На экран Домой».
- Повторить три обновления подряд; сверить покупки, продажи, ремонты, расходы, аксессуары, кассы, журнал, настройки, черновики и резервные копии.
- Проверить отмену подтверждения в покупке, продаже, ремонте, редактировании и импорте; подтвердить обновление только после сохранения нужных полей.
- Проверить «Позже», возвращение из сна/bfcache, две вкладки/PWA-окна, клавиатуру, поворот iPhone, safe-area, светлую и тёмную темы.
- Оборвать сеть при скачивании, запустить старую версию офлайн, восстановить сеть и завершить обновление; проверить нехватку диска/квоты в тестовом профиле.
- Проверить, что Pages отдаёт именно Vite dist на прежнем origin/scope; не менять URL ради обновления. Отдельно убедиться в панели Cloudflare, что демопроект не настроен на автопубликацию этой ветки: внешние настройки Cloudflare из этого репозитория не видны.

Публикация и merge требуют отдельного решения владельца. Результаты автоматических прогонов приведены в PR.
